# Plan: lobbies (several games at once, seats, spectators, new menus, How to play) (2026-10-02)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development, under workflow v1.4
> (`C:\UniStuff\Y3\MinorSkilled\Resources\core\`): one brief file per task in `Resources/loops/Limit Test/briefs/`, one
> sonnet implementer under the Editor lock, one read-only **opus** review per task (lobbies and match rules are shared
> between players, so every task counts as networking), fixes re-reviewed, the controller's own check, logged, one commit
> per task, push after the review's fixes land.

**Goal (play terms):** players pick a name, browse a live list of lobbies or create one (name + mode), take a team seat or
a spectator seat or stay in "No role", and the lobby's host starts the game (everyone spawns into the warm-up, the
unseated are placed automatically) and later ends the warm-up; several lobbies play at once; spectators watch the whole
map; after the match everyone returns to the list. New name screen, lobby screens, chat and a How to play wiki in
Oswald + Public Sans. Capturing with teammates speeds up 1 / 1.5 / 1.75 instead of 1 / 2 / 3.

**Architecture:** one Photon room per lobby; every shared fact is a Room or Player Property (no RPC added, renamed or
removed; RpcList byte-identical, 45). Modes are data (`GameModeDefinition` assets in a `GameModeCatalogue`). Seats are
Room Properties claimed by check-and-set. Pure rules in plain C# (`Assets/scripts/Lobby/Rules/`, edit-mode tested); thin
Photon wiring around them; UI built in code (uGUI + TMP) like today's panels.

**Tech stack:** Unity 6000.0.70f1, URP, Photon PUN 2 + Photon Chat, TextMeshPro, NUnit edit-mode tests.

**Spec:** `docs/superpowers/specs/2026-10-02-lobby-design.md`. **Mockups + picks:**

## Rules that bind every task (HANDOFF §1)

The Editor lock first, in a command of its own (`editor-lock.ps1 take -Owner "..."`, read "TAKEN"), released last after
`list_open_scenes` shows `Assets/Scenes/Game Scene.unity` not dirty and Play Mode stopped (poll after tests, F29). No
script or asset edit while the Editor is in Play Mode (the hook refuses it). Tests: `unity command run_tests -- --mode
editor --async_tests true` only, one run at a time, bounded polling of `test_status`. Never the real mouse/keyboard/
focus, never `editor_focus`; drive UI by calling its methods; aim with `PlayerAim.SetAimOverride`, move with
`PlayerDisplacement.TeleportTo`. **No `[PunRPC]` added, renamed or removed.** Never stop a process by name; never print
Photon App IDs (Realtime or Chat) or a full user id (8 characters at most). Tudor's uncommitted changes are his: `git add`
by path only. Builds only in `Builds/ClientN`; the runtime server on for a dev build only, off right after, never
committed; never the testers' build. Tests guard rules, never Tudor's numbers. New serialized fields go into assets/
prefabs as hand-edited YAML lines, then grep (trap 8). Every multi-client check: list the room's actors first (Tudor may
be playing), recorders on every client before acting, a fresh process for any join/rejoin (F27), captures looked at with
a "what is in frame" line. Two lobbies at once = two rooms side by side, at most 4 clients in all (Photon's 20 is shared
with Tudor). Commits carry the implementer's own model trailer; messages from a file without a BOM.

## Risks
- Photon's room list arrives only while in the lobby and only as changes: the cache must be cleared on leaving it.
- Players carry Player Properties into the next room (`teamID` was kept on purpose): A3 clears it on joining.
- Two masters in one instant can both write a Start: the check-and-set on `lS` keeps one.
- Photon Chat is a second connection; a room change must unsubscribe before subscribing.

## Out of scope
Dominion (own spec/plan), mode switching in a lobby, passwords, kicking, team changes after Start, rematch in the same
lobby, How to play in a match.
